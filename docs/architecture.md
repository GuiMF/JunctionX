# Architecture and data contract

QuantumTrace runs three bounded discovery adapters through one Python assessment
pipeline. Source code, saved captures and AWS JSON snapshots become `AdapterResult`
objects; `ScanService` validates, assesses and deduplicates their findings, computes
asset exposure, and returns a `ScanResult`. FastAPI exposes that pipeline over HTTP.
The CycloneDX exporter converts the assessed result into a validated CBOM.

The React dashboard currently displays generated fixtures. File selection does not
submit scans. Its scan and CBOM data come from `examples/`; its migration comparison
is generated by scanning the original and modified raw cloud snapshots. Configuration
changes do not establish observed network negotiation.

| Location | Responsibility |
| --- | --- |
| `adapters/` | Source, capture and cloud detection; fixture import; scanner registry |
| `core/` | Shared Pydantic models, assessment, identity, scoring and scan service |
| `api/` | HTTP routes and local CORS configuration |
| `export/` | CycloneDX 1.6 conversion and offline validation |
| `web/` | React dashboard and UI-specific types |
| `cloud-posture/`, `tests/fixtures/` | Canonical synthetic inputs and independent expected labels |
| `examples/`, `schemas/` | Generated integration examples and data contracts |
| `scripts/` | Startup, scans, evaluation and artifact generation |
| `tests/`, `web/tests/` | Backend and frontend regression checks |
| `reports/` | Ignored local outputs |

`core/models.py` is the contract source of truth. `python -m scripts.generate_contract`
regenerates JSON schemas, examples, the migration comparison, and
`web/src/types/generated.ts`. Frontend aliases derive from those generated types;
`ui.ts` contains only presentation types. CI checks generated artifacts for drift.
The TypeScript generator supports the schema forms used by these models and fails
on unsupported forms rather than silently widening them. Backend `Any` remains `any`.

The cloud parser and shared adapter live together in `adapters/cloud.py`. Its
standalone directory report remains available for diagnostic and migration tools;
its `cloud_adapter` function returns the common `AdapterResult` for the core.
`network-capture.py` now returns a complete assessed `ScanResult`, matching the API,
with exit code 1 on a partial or failed scan.

Validation stays at request, adapter and export boundaries. Structural validity is
separate from detector accuracy and cryptographic assessment. The source evaluation
uses independently authored labels; passing an export schema is not proof of safety.

## Shared contract v1

The source of truth is `core/models.py`. Generated JSON schemas live in `schemas/`.
Examples under `examples/adapters/` show the shape for each scanner owner. All built-in adapters use this contract.

## Objects and ownership

| Object | Meaning | Filled by |
| --- | --- | --- |
| `ScanInput` | Named inline file content, source type, raw/normalized format, encoding | API caller |
| `AdapterContext` | Fixed timezone-aware evaluation time | Core |
| `Finding` | One algorithm occurrence, usage, parameters, exact supporting evidence | Adapter, then core assessment |
| `AdapterResult` | Findings, coverage, errors, explicit relationships, detector versions for one input | Adapter |
| `ScanRequest` | Inputs, optional evaluation time, label and synthetic flag | UI or script |
| `ScanResult` | Full assessed result, versions, hashes, score, errors, coverage and provenance | Core |

`source_type` is `source`, `pcap`, or `cloud`. All fields reject unknown extra keys.
Evidence requires a nonempty `file`, `locator`, and `detail`; `file` is provenance,
not permission to read that path. Use line locations, frame/stream identifiers, or
JSON pointers. Evidence must substantiate the finding without including secrets.

Use canonical algorithms where possible, such as `AES` plus `key_bits: 256` and
`mode: GCM`. Sizes are **bits**, iterations are positive integers, and missing
parameters are `null`. The current optional parameters are `key_bits`, `mode`,
`named_group`, `hash_algorithm`, `iterations`, and `configured_tls_policy`.

`configured_tls_policy` describes a documented configuration capability, including
protocols, cipher membership, hybrid groups, classical fallback and mapping source.
It is optional for other adapters. `negotiated_group` must be null: this field cannot
assert a selected group. The finding's `named_group` also stays null when selection
is unknown. The core preserves the descriptor without treating a hybrid-capable
listener as an observed hybrid connection or PQ certificate authentication.

Adapters set identity, source, algorithm, parameters, usage, evidence kind,
evidence, confidence, ownership, observation time, and any independently evidenced
classical/posture issues. The core overwrites quantum status, challenge tier,
rule ID, rationale and recommendation using its versioned rules. Default quantum
fields are `unknown`; pending explanations are `null`. Core rules add classical
issues without discarding detector-supplied ones.

## Meaning of evidence and uncertainty

| Value | Meaning |
| --- | --- |
| `declared` | Source-level declaration; runtime execution unverified |
| `configured` | Configuration snapshot; actual runtime use unverified |
| `offered` | Capability advertised by a peer; selection unverified |
| `observed` | Observation of the specific captured operation |
| `null` | A scalar fact is unavailable |
| `unknown` | A classification cannot be established |
| `not_applicable` | That assessment dimension does not apply; not a safe result |

`observed_at` records the evidence timestamp and stays null when unavailable. For
cloud input, retain the export timestamp, not the time of this scan. `started_at`
is the actual scan start; `evaluated_at` is the explicit evaluation time used for
time-dependent checks. Use `context.evaluated_at` in adapter expiry logic. All
timestamps need a timezone.

An empty issues list means no issues were reported by these checks. It is not
a proof of secure implementation. `confidence` describes detection confidence;
the core preserves it rather than promoting it based on algorithm recognition.

## Stable identity and repeated observations

Use `stable_asset_id(source_type, identity)` (or an immutable cloud ARN) with a stable logical resource or
occurrence identity: an ARN, a repository-relative symbol/call-site identity,
or a capture/flow identity. Do not use a mutable algorithm, current key size,
timestamp of the scan, array index that may reorder, or entire file hash as an
asset identity. A network capture hash plus stream can identify a flow inside
one capture; matching flows across different captures requires explicit evidence.

Use `stable_finding_id(asset_id, usage, slot, evidence_kind)` for a stable role
such as `signing-key` or `selected-group`. Independent occurrences and multiple
offered candidates need distinct slots. Keep the role stable when configuration
changes so before/after comparison matches the same finding. Offered and observed
observations always have different IDs.

Deduplication merges repeated **finding IDs** only, retaining distinct evidence,
all issues, a known consistent owner, latest observation time and the lower
confidence. Different facts or conflicting non-null owners under the same finding
ID within a scan reject the offending input. Different facts under the same ID
across two scans are expected during migration. The score separately deduplicates
asset IDs, so multiple findings on one asset cannot inflate its weight.

Explicit relationships contain `source_asset_id`, `target_asset_id`, `kind`, and
nonempty evidence. Unresolved targets remain visible. Similar names or shared
algorithms are not grounds for creating a relationship.

## Inventory and snapshot provenance

`AdapterResult` and `ScanResult` also accept optional `assets` and `snapshots` lists.
These default to empty lists for existing adapters. Inventory assets preserve their
stable ID, source type, resource kind, explicit parent, owner, snapshot time,
account/region, configuration and evidence. Cloud assets use their immutable ARN
as identity. Load balancers can be inventoried without inventing a cryptographic
finding. The score still counts findings' assessed asset IDs; inventory coverage
is separate and inventory-only assets must not be presented as assessed or safe.

Snapshots identify their input name, source type, evidence file/JSON pointer,
`generated_at` and `age_seconds` relative to `AdapterContext.evaluated_at`.
Negative age means evaluation predates the export. For configured cloud findings,
`observed_at` is the snapshot's `GeneratedAt` as specified above, not a claim about
wire negotiation. The input hash covers the submitted decoded bytes. Both JSON
and CycloneDX preserve inventory and snapshots (CBOM metadata properties).

Unresolved certificate ARNs remain relationship targets and have explicit scan
errors; absence from `assets` identifies the unresolved target. A malformed or
missing target with no usable identifier has an error without an invented edge.

## Coverage and errors

Report coverage by input, source type and unit (`files`, `sessions`, `packets`,
`resources`, or `inputs`). Within each reported population, `assessed`, `unknown`,
`unsupported`, and `failed` are disjoint nonnegative integer counts. If reporting
both sessions and packets, use separate entries; never sum them into a percentage.

Coverage describes the adapter's input processing, while quantum unknown counts
describe the assessment of detected assets. For example, a successfully processed
session can contain known key exchange and unknown authentication. A successfully
checked file with no finding is not an inventoried safe asset.

Errors identify `source_type`, `input_name`, `code`, and a concise non-secret
`message`. An unavailable parser reports one unsupported `inputs` unit because
the true file/session/resource population is not known. An input failure preserves
other successful inputs. Requests with invalid structure are rejected before scanning.

Registration details and JSON transport are in [the API guide](api.md).

## Report exports

The API supports project JSON and CycloneDX 1.6. Project JSON is the complete
`ScanResult.model_dump(mode="json")` contract. For CBOM use
`export.cyclonedx.export_cyclonedx(scan)`; it returns a dictionary **after validating**
it against the full pinned schema. `validate_cyclonedx(document)` is also public.

## CycloneDX mapping

Each normalized finding becomes one `cryptographic-asset` component identified by
`quantumtrace:finding:<finding.id>`. Separate occurrences stay separate, even when
they use the same algorithm. The original asset ID is retained as
`quantumtrace:asset_id`, permitting consumers to group findings on one resource.
This exporter does not invent certificate/key component types from asset names:
the Finding contract describes algorithm occurrences, not full certificate/key
records. Explicit TLS/SSH observations can be represented as protocol assets.

Exact normalized names share the assessment engine’s pinned taxonomy and map
to the standard primitive field. Embedded AES parameters (for example
`AES-256-GCM`) and supplied parameters map to standard algorithm properties.
Conflicting embedded/supplied AES facts produce primitive `unknown` without
choosing either parameter value; both original claims survive in properties.
Family-like names such as `AES-SOMETHING` are not accepted as known primitives. Unknown algorithms retain
their original name and primitive `unknown`. Unsupported modes become `other`
while the original value remains in project properties. A key length is never
reported as a security-strength value. No NIST quantum level is inferred.
An ambiguous curve/group name such as `P-256` becomes `key-agree` only for
key-establishment usage; a signature observation is not relabeled as key
agreement. Cipher modes on known non-cipher primitives are retained only in
project properties, rather than attached to standard signature/hash/KEM fields.

Exact evidence files become standard component `evidence.occurrences`; their
locator, detail, and evidence kind remain in `additionalContext`. All finding
fields, including evidence, owner, nulls, quantum status, classical issues,
posture issues, parameters, recommendation, and references, also survive as
`quantumtrace:<field>` properties. Strings are stored literally; objects, arrays,
nulls, numbers and booleans use JSON text. These properties are the authoritative
lossless representation of the shared project contract.

Scan fields other than findings are retained in metadata properties, including
coverage, errors, scores, tool/rule versions, input hashes, synthetic labels,
and explicit relationships with their evidence. This preserves unresolved
references and typed relationships without guessing links. Only `depends_on`
relationships whose two asset IDs each resolve to exactly one component also
become standard dependency edges. Other kinds, unresolved targets, and assets
with multiple algorithm components remain in the project relationship list.
Omitted dependency nodes mean unknown dependencies, not proven absence.

The report timestamp is the scan's evaluation timestamp. A UUIDv5 serial number
is generated from the canonical exported content; identical reports produce
identical output and changed exported content gets a different serial number.
Finding input order does not affect the serial because components are sorted
by finding ID. Order in other lists is retained as part of their evidence or
metadata. No wall
clock, random ID, external service, or file beyond the vendored schema is used
while exporting.

## Offline validation and provenance

Schemas are unmodified copies from the official [CycloneDX specification tag
1.6](https://github.com/CycloneDX/specification/tree/55343ba19dee1785acf1ce9191540d5fd7b590db/schema),
pinned to commit `55343ba19dee1785acf1ce9191540d5fd7b590db`. The full BOM schema,
SPDX schema, and JSF schema are vendored under `schemas/vendor/cyclonedx-1.6/`.
`manifest.json` records exact URLs and SHA-256 hashes; `LICENSE` retains the
upstream Apache-2.0 license. Original embedded attribution remains in each file,
including JSF attribution to Anders Rundgren/OpenKeyStore.

Validation uses the complete Draft 7 schema, date-time/URI format checks, and a
local `referencing.Registry` with no network retriever. The minimal dependency
set does not install the optional IRI-reference format checker; IRI syntax in
externally supplied fields outside our export mapping is therefore not checked.
The exporter itself does not produce fields requiring that checker. Additional checks enforce version 1.6, unique
`bom-ref` values, and resolved local dependency edges, which JSON Schema alone
cannot guarantee. Schema violations raise `jsonschema.ValidationError`;
reference/version violations raise `ValueError`. Schema validation does not
verify cryptographic signatures or prove that a detector's findings are true.

Run `python -m pytest tests/test_export.py` in the project environment. The tests
exercise minimal/populated exports, unknowns, evidence/relationships, ambiguous
and unresolved links, malformed reports, provenance hashes, and both external
schema references with network access disabled.
